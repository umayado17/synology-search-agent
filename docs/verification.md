### 検索 API の応答の形（DSM 7.4.1）

- `data` のキー: `has_error`、`hits`、`total`、`unavail`
- `hits` の要素は平らなオブジェクト。頼んだ5つのフィールドのほかに `SYNOMDExtension`、`SYNOMDOwnerUserID`（null）、`SYNOMDPath`（`/volume1/<共有>/...`）、`additional`（`doc_id` など）、`readable` も返る
- `SYNOMDSharePath` は `/<共有フォルダ>/<途中のパス>/<名前>` の形で、名前まで含む
- 値の型: 日時は UNIX 秒の**文字列**、サイズも**文字列**（フォルダは `"4096"`）、`SYNOMDIsDir` は `"y"` / `"n"`
- インデックス作成中は `total` が数分のうちに変わった

テスト用の応答データ（`tests/fixtures/search_response_sample.json`）は、この形のまま架空のパスにしたものです。

## 検索範囲の確認（2026-11-04）

検索専用の DSM ユーザー（グループ `users` のみ・2段階認証あり）で試しました。

- **検索結果はログインしたユーザーの権限で絞られる**ことを確認した
- 共有フォルダ `homes` を読めるようにすると、全ユーザーのホームが結果に出た。DSM の権限では `homes` の中の特定ユーザーだけを許すことはできない。そのため検索させたいファイルは別の共有フォルダに移した
- `users` グループ経由で読める共有フォルダも結果に出た。検索専用ユーザーに個別に「アクセスなし」を設定すると消えた
- 結論: DSM の権限で範囲を絞り、さらに CLI の `--allow-prefix` でも絞る（二重の守り）

### 権限の分離（6-2）

許可していない共有フォルダにあるファイルの名前（作者が指定）で検索しました。結果の最後のページまでたどり（100件ずつ、数千件）、すべて許可した共有フォルダの中で、同じ名前のファイルは0件でした。返ってきたのは、本文に同じ語を含む別のファイルです。重複もありませんでした。

ただし、検索専用アカウントからはそのファイルが見えないため、そのファイルが索引に入っていることは、このアカウントからは確かめていません。

### ページ送り（6-3、索引が変わらないとき）

結果が数百件ある日本語の語で、`--max-results 300` の 300 件と、`--limit 20` で 15 ページたどった 300 件を比べました。

- どちらも重複なし（300 件すべて別のファイル）
- 並び順が同じ

100件ずつのページ送りでは、1ページに約 5 秒かかりました（範囲外の結果を読み飛ばす分を含む）。

### 索引が更新されている最中のページ送り（6-4）

許可した共有フォルダにテスト用のフォルダを作り、名前に同じ語を含むファイルを置きました。その語で検索すると、テスト用のファイルだけが結果に出ます。この状態で、ページとページのあいだにファイルを増やしたり消したりしました（1ページ4件）。

- 索引に入るまでの時間: 置いてから約 18 秒、消してから 1 分以内に、検索結果に反映された
- 並び順: ファイル名の番号の順ではなかった。追加したファイルは、結果の最後に付いた
- **追加**（10 件 → 15 件）: 2ページ目は、追加する前の順番どおり。重複 0 件、取りこぼし 0 件
- **削除**（1ページ目に出ていた 2 件を消す）: 残りが 2 つずつ前に詰まり、2ページ目は 2 件先から始まった。重複 0 件、**取りこぼし 2 件**（消していない 2 件が、どのページにも出なかった）

この回は、追加したファイルが結果の最後に付いたので、重複は起きませんでした。追加したファイルが前のほうに入れば、重複が起きると考えられますが、この確認では起きていません。原因は断定しません。

結果の多い語（「報告書」など、数千件）では、追加したファイルが上から 4,000 件の中に入らず、ページ送りへの影響は見えませんでした。

### 共有フォルダ A について

検索セッションは2つの共有フォルダ（ここでは A と B）を許可して始めましたが、どの語で検索しても、A のファイルは出ませんでした。Universal Search の画面では A は索引の対象に入っていたので、検索専用アカウントから読めない設定のためです（2026-11-04 に、`users` グループ経由で読める共有フォルダを、検索専用アカウントだけ「アクセスなし」にしたことと合います）。DSM の権限が、`--allow-prefix` より先に効いていることの確認にもなりました。

## 検索を速くする試み（2026-11-06〜07、v0.9.0 の開発中）

1回の検索のおおよその内訳（この Mac から、Tailscale 経由）: ssh の接続 約 0.47 秒、NAS の入口と検索セッションの受け渡し 約 0.1 秒、DSM の検索 API 1回 約 1.1 秒。5件で約 1.7 秒、100件（API 2回）で約 2.9〜3.3 秒でした。

**ssh の接続の使い回し（採用）。** 検索だけの鍵（`restrict,command=...`）でも使い回せました。

| 確認 | 使い回しなし | あり |
|---|---|---|
| `--status` | 0.61 秒 | 0.33 秒 |
| 5件の検索 | 約 1.7 秒 | 約 1.5 秒 |
| `--max-results 300` | 約 8.6 秒 | 約 7.6 秒 |

**DSM に頼む件数を絞る（不採用）。** 範囲外の結果に出会うまで、DSM に要る件数（+1）だけを頼む形を試しました。NAS の中で、今の 90 日のセッション（v0.7.0）と、試しの 1 時間のセッション（絞る版）に同じ検索を交互に 5 回ずつ送り、真ん中の値を比べました。

| 検索 | 今 | 絞る版 |
|---|---|---|
| `test`、5件 | 1.26 秒 | 1.23 秒 |
| `test`、20件 | 1.26 秒 | 1.24 秒 |
| `test`、100件 | 2.39 秒 | 2.35 秒 |
| `pdf`、5件 | 1.03 秒 | 0.99 秒 |

差は 2〜4% で、ばらつきの範囲でした。DSM の時間は頼む件数よりも呼ぶ回数で決まるようなので、この変更は入れていません。試しのセッションは止め、試しのファイルは消しました。
