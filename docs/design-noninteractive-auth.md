# 設計: 外部AIエージェント向けの非対話認証

状態: 案C（セッションブローカー）＋案D（検索専用アカウント）を採用し、v0.4.0 で実装。2026-11-05 に実機で動作を確認（`docs/verification.md`）。導入手順は `docs/agent-setup.md`。

## 1. 課題

ゴールは `ssh <nas-host> synosearch --json QUERY` を外部エージェントが TTY なしで実行し、JSON を得ること。現状は検索のたびに DSM のパスワードと OTP（2FA）が必要で、非対話では成立しない（終了コード7）。

守るべき条件（AGENTS.md）: sudo/root 不要、2FA を解除しない、パスワード・OTP・SID をコード/ログ/出力に残さない、認証回避や Cookie 抽出をしない、インデックスや共有フォルダを変更しない。

## 2. 脅威モデル（要点）

| 資産 | 漏れた場合 |
|---|---|
| DSM パスワード | 本人の全権限（Web UI・File Station 書き込み等）。2FAが最後の防壁 |
| TOTP シード | 2FA の無効化と同義 |
| SID（FileStation セッション） | 有効期間中、File Station API で本人権限の**読み書き**が可能 |
| エージェント用 SSH 鍵 | NAS 上で本人ユーザーとして任意コマンド実行 |

重要な前提: **エージェント用 SSH 鍵を持つ者は、そのユーザーのホーム内の資料をすべて読める**。したがって NAS のホームに置いた秘密（パスワードファイル等）は SSH 鍵と同じ強さでしか守られない。SSH 鍵の権限を絞ることが全案共通の土台になる。

## 3. 選択肢

| 案 | 概要 | 2FA | 漏洩時の影響 | 判定 |
|---|---|---|---|---|
| A | パスワード＋TOTPシードを NAS に保存し OTP を自動生成 | 実質解除 | 恒久的に本人全権限 | **却下** |
| B | `SYNO.API.Auth` のデバイストークン（信頼済みデバイス）＋保存パスワード | 初回のみ | パスワード流出＋OTP省略 | 保留（下記） |
| C | **人が OTP で開始したセッションを常駐プロセスがメモリ保持（セッションブローカー）** | 毎回人が通す | 期限内の SID のみ。期限で自然失効 | **推奨（第1段階）** |
| D | 検索専用の DSM 低権限アカウント（読み取り専用共有のみ）＋保存パスワード | アカウント設計次第 | 読み取り範囲に限定 | 第2段階の候補（DSM 設定変更を伴うため本人判断） |
| E | 検索インデックス（synoelasticd 等）を直接読む | 回避 | ACL を迂回 | **却下**（認証回避・root 相当） |

案Bは DSM 正規機能だが、保存パスワードの流出が「2FA 済み端末からのログイン」に直結し、AGENTS.md の趣旨（2FAを解除しない）に抵触しうる。API パラメータ（`enable_device_token` / `device_name` / `device_id`）の挙動は**実機未確認**。

## 4. 推奨: 案C セッションブローカー

```
[本人] ssh -t <nas-host> synosearch session start   ← パスワード＋OTPを本人がTTY入力
          │ ログイン(FileStation) → SID をプロセスのメモリにのみ保持
          ▼
 synosearch-broker（一般ユーザーの常駐プロセス, root不要）
   UNIXソケット $XDG_RUNTIME_DIR or ~/.synosearch/broker.sock (0600, ディレクトリ 0700)
          ▲
[エージェント] ssh <nas-host> synosearch --json QUERY   ← TTY不要。ソケット経由で検索依頼
```

設計の要点:

1. **SID はファイルに書かない**。ブローカーのメモリにのみ保持し、ソケット応答にも含めない（ソケットで受けるのは検索条件、返すのは検索結果のみ）
2. ソケットはブローカーが受け付ける操作を `search`（limit/offset 上限つき）と `status` に限定。任意 API の中継はしない（SID の権限＝File Station 読み書きを外へ出さない）
3. 接続元確認: ソケット 0600 ＋ `SO_PEERCRED` で同一 UID のみ許可
4. 期限: 最大寿命（例 8 時間、設定で短縮のみ可）とアイドル失効。期限到来・`session stop`・プロセス終了で必ずログアウト
5. キープアライブは最大寿命内でのみ。DSM 側のセッション失効時間は**実機で計測してから**決める（未検証）
6. セッション未確立時、エージェント側は即座に `{"error":{"type":"session_required"}}`・専用終了コード（例 8）で失敗し、人に `session start` を促す
7. 監査: ブローカーは検索語と件数・時刻のみを 0600 のログへ（SID・資格情報は記録しない）。検索語自体が機微な場合に備えオフにできる
8. NAS 再起動・ブローカー停止時は自然にセッション消失（安全側に倒れる）

CLI 追加案:

```
synosearch session start [--max-age 8h]   # 対話（TTY必須）
synosearch session status [--json]        # 非対話
synosearch session stop                   # 非対話、即ログアウト
synosearch QUERY --json                   # ブローカーがあれば利用、無ければ従来の対話 or exit 8
```

## 5. SSH 側の権限境界（全案共通・本人の承認が必要）

- エージェント専用の SSH 鍵を新規発行し、`~/.ssh/authorized_keys` で次のように制限する:
  `restrict,command="$HOME/.local/bin/synosearch --agent-gateway" ssh-ed25519 AAAA... agent`
  （`--agent-gateway` は `SSH_ORIGINAL_COMMAND` を解析し、検索/状態確認のみ許可する入口。シェルは渡さない）
- `restrict` でポート転送・PTY・エージェント転送を禁止 → エージェントはブローカーのソケットに直接触れず、ゲートウェイ経由のみ
- 鍵の失効＝`authorized_keys` から1行削除。DSM 側の設定変更は不要
- これは NAS 上のファイル（`authorized_keys`、`~/.local/bin/synosearch`）の追加を伴うため、検証手順完了後に本人が行う

## 6. 残るリスクと未確認事項

- **実機所見: DSM で SSH を使えるのは `administrators` グループのユーザーだけ。** このユーザーのセッションや SSH 鍵をエージェントに使わせると、漏洩時の影響は管理者権限に及ぶ。案C でもソケットで操作を検索に限定することが必須で、長期運用では案D（検索専用の非管理者アカウント）を優先して検討すべき
- ブローカーは本人ユーザーで動くため、**本人のSSHシェルを奪った攻撃者**はプロセスメモリから SID を読める（同一UID）。案Cはそれを防がない。防ぐには案D（別アカウント）＋別 UNIX ユーザー化が必要だが、DSM のユーザー追加は管理者操作
- DSM の FileStation セッションの失効時間・同時セッション数上限・IP 紐付けは未検証
- 一般ユーザーの常駐プロセスが DSM により終了されないか（ログアウト時の kill 等）は未検証。`nohup`/`setsid` で足りるか要確認
- DSM 更新で非公開 API の応答が変わる可能性（`--check-api` を定期的に実行）

## 7. 実施順（承認後）

1. `docs/nas-verification.md` の手順1〜5を完了（対話CLIの実機成立）
2. DSM セッション失効時間・常駐プロセス存続を対話で計測（読み取りのみ）
3. 本設計の承認 → ブローカーとゲートウェイを実装・テスト（ソケットは偽物で単体テスト）
4. 本人が `authorized_keys` に制限付き鍵を追加して試験運用

## 8. 決定事項

- **案D（検索専用アカウント）を採用**。DSM ユーザーはグループ `users` のみ・2段階認証あり。案C（セッションブローカー）と組み合わせ、1日1回程度は本人が OTP でログインする
- SSH の入口は本人の SSH ユーザーのまま（DSM では SSH は administrators のみ）。エージェント用の鍵は `restrict,command=` で検索の入口に限る（5章）。DSM API へのログインは検索専用アカウント
- **実機所見**: 共有フォルダ `homes` を読めるようにすると、全ユーザーのホームが検索結果に出る。DSM の共有フォルダ権限では `homes` の中の特定ユーザーだけを許せない。検索させたいファイルは専用の共有フォルダに置き、検索専用アカウントにはそこだけ読み取りを許す
- `users` グループ経由で読める共有フォルダも結果に出るため、検索専用アカウントに個別に「アクセスなし」を設定する
- 多層防御として、CLI 側でも許可したパスの接頭辞（`--allow-prefix`）以外の結果を捨てる
- インデックス作成中は総件数が変わる。インデックス作成は root 所有の `@eaDir` に書き込むため、同じ時期に大量のファイル変更が見えることがある
