# 背景：Universal Search を AI エージェントに渡すまで

このツールを、なぜこの形にしたのかをまとめます。2026-11-04 から 11-05 にかけて、作者の NAS（Synology DS225+、DSM 7.4.1）で試した経過がもとです。数字は、作者の環境で一度測った値です。

全体は3つの層でできています。

| 層 | 中身 | 章 |
|---|---|---|
| 接続 | エージェントから NAS に SSH で届く道（作者の環境では Tailscale） | 0 |
| 索引 | Universal Search が作る全文検索の索引 | 2〜3 |
| 権限 | 検索専用の DSM アカウントと、検索しかできない SSH 鍵 | 4 |

## 0. 前提：エージェントから NAS に届く道

AI エージェントは、クラウドの仮想マシンで動いています。NAS は自宅の LAN の中にあります。そのままでは届きません。

作者の環境では、[Tailscale](https://tailscale.com/) で仮想のネットワーク（tailnet）を作りました。エージェントの仮想マシン、NAS、手元の Mac と Windows を同じ tailnet に入れています。これで、仮想マシンから NAS に、家の LAN の中にいるのと同じように SSH が届きます。

- **NAS はインターネットに公開しません。** ルーターのポートは開けず、届くのは tailnet に入った自分の機械だけです（作者が、認証なしで入れる入口が閉じていることを確かめました）
- **手元の Mac や Windows は、初めの設定に使います。** DSM で SSH を有効にする、公開鍵を登録する、索引を作るフォルダを指定する、検索セッションを始める（パスワードと2段階認証のコードを入力する）。こうした「人が一度だけする作業」は手元の機械からします。ふだんの検索は、仮想マシンから NAS への直通です
- **NAS をどのネットワークに置くかは、「いま実際に安全に運用できるのはどちらか」で決めました**

このツール自体は Tailscale を必要としません。エージェントから NAS に SSH で届けば、どの方法でもかまいません。ただし、NAS の SSH をインターネットに直接公開することはすすめません。検索の話は、この道があって初めて成り立ちます。

## 1. 出発点：AI エージェントに NAS の中を探させたい

AI エージェントは SSH で NAS に入れます。ただ、`find` や `grep` は、そのたびにファイルを走査する検索です。

- ファイル名の検索（`find`）は、思ったより速いです。作者の環境では、約169万ファイル・1.76TB の共有フォルダを全部走査して12〜15秒でした
- 本文の検索（`grep`）は、検索のたびに全部のファイルを読みます。データが大きいと使えません

必要なのは逆の形です。NAS があらかじめ索引を作っておき、エージェントは索引に問い合わせます。返ってくるのは、名前・パス・更新日などの短い情報だけです。中身を読むのは、必要になったファイルだけにします。

つまり、やりたかったのは「検索エンジンを作ること」ではありません。「すでにある索引を、AI から使えるようにすること」でした。

## 2. Universal Search：よい索引があるのに、AI から使う入口がない

Synology の Universal Search（パッケージ名 `SynoFinder`）は、DSM 7 では通常、最初から入っています（くわしくは [README](../README.md#使う前の準備nas-側)）。指定した共有フォルダについて、ファイル名だけでなく文書の本文まで索引にします。DSM の画面から使うと便利で、索引の更新も Synology 側がしてくれます。

ところが、プログラムから使う公開された入口がありません。

- SSH の普通のコマンドは、この索引を使いません
- DSM には `/usr/syno/bin/synosearch` というコマンドがありますが、これはヘルプを検索するもので、別物です。このツールの名前も `synosearch` なので、まぎらわしい点に注意してください（[README の注意](../README.md#使う前の準備nas-側)）

もう1つ、落とし穴があります。**索引を作る共有フォルダを指定しないと、索引は作られません。** Synology の公式ヘルプにも、索引を作っていないフォルダのファイルは検索結果に出ないこと、File Station や SMB で使うフォルダは自分で索引の作成（Indexing Task）を作る必要があることが書かれています（[File Indexing](https://kb.synology.com/en-global/DSM/help/SynoFinder/universalsearch_index?version=7)）。作者の NAS でも、パッケージは動いていたのに、索引の対象フォルダが0件で、索引のデータは約2.8MB しかありませんでした。「入っているのに検索できない」原因はこれでした。

自分で全文検索の索引を作る案（sist2 と SQLite FTS5 など）も考えました。しかし、索引を2つ持つと、CPU・保存場所・手入れも2倍になります。使える索引がすでにあるなら、まずそれを使うことにしました。

## 3. 試してみた：内部の API を呼ぶと、索引がそのまま検索エンジンになった

DSM の内部には、索引を検索する API `SYNO.Finder.FileIndexing.Search`（version 1）があります。本文（`SYNOMDTextContent`）にも重みをつけて検索でき、結果はパス・名前・サイズ・更新日を含む JSON で返ります。ただし、公開されていない仕様です。

先に作られた例として、[atkaper/synology-universal-search-cli](https://github.com/atkaper/synology-universal-search-cli)（2021年）がありました。2021年5月から更新されていないため、スクリプトはそのまま使っていません。参考にしたのは、「この API があって、呼び出せる」という点です。

作者の NAS で試したこと:

1. 共有フォルダを1つ索引の対象にして、索引を作らせた
2. 作者が root のシェルで `synowebapi --exec` を使い、この API を呼んで、成功が返ることを確かめた
3. 索引ができたあと、ある英単語で47件見つかった。名前にその単語を含まない文書も、本文が一致して返ってきた

これで「Synology の索引を、AI の検索エンジンとして使える」ことが分かりました。残った問題は権限だけです。

## 4. 権限：root を渡さず、検索だけを渡す

試すときに使った `synowebapi` は、root しか実行できません（`root:root`、権限 `700`）。AI エージェントに root を渡すことはできません。エージェントに必要なのは「索引を検索すること」だけで、シェルも管理者の権限も要りません。どう絞るかが、設計の中心です。

### 最初の形（今は使っていない）

最初は、検索だけをするラッパーを root の持ち物として置きました。検索語だけを受け取り、決まった条件で API を呼びます。そして sudo で「このラッパーだけ、パスワードなしで実行してよい」と許可しました。

これで動きましたが、弱いところが残りました。

- 置くときに root の作業が要る
- DSM を更新すると、sudo の設定が消えるおそれがある
- 特権で動くプログラムが1つ増える

そのため、このリポジトリではこの形を**使いません**。sudo も root も求めない形に作り直しました。

### このリポジトリの形

特権を使うこと自体をやめました。

- **一般ユーザーとして API を呼ぶ**：同じ API を、root を通さずに、DSM Web API（`https://127.0.0.1:5001`）から一般ユーザーとして呼びます
- **検索専用の DSM アカウント**：管理者にしない、2段階認証をかける、検索させたい共有フォルダだけを読めるようにする、ほかは「アクセスなし」にする。権限で守る中心は DSM の共有フォルダの権限で、CLI の `--allow-prefix` は補助です
- **ログインは人がする**：「検索セッション」を人が始めます。パスワードと2段階認証のコードは人が入力します。有効期間は既定で8時間です。SID は検索セッションのメモリの中だけに置き、ファイルにもログにも残しません。期限が切れたら、人が始め直します。AI は認証情報をまったく持ちません
- **エージェント用の鍵は検索しかできない**：`authorized_keys` の `restrict,command=` で、検索の入口だけを実行させます。シェル、ポート転送、ほかのコマンドはすべて断ります
- **sudo も root も要らない**：本体の CLI は、SSH ユーザーのホーム（`~/.local/bin`）に一般ユーザーの持ち物として置きます

### 索引の範囲も絞る

全部を索引にはしません。

- データベースやコンテナの中身がある共有フォルダは、本文を検索しても意味がなく、負荷や競合の原因になるので対象外にした
- 原本が別の場所にあるバックアップ用の共有フォルダも対象外にした
- 実際に使う文書がある共有フォルダだけを対象にした

**索引の対象にすることと、検索専用アカウントに読ませることは別の設定です。** 作者の環境では、検索専用アカウントに共有フォルダ `homes` を読めるようにすると、全員のホームフォルダが結果に出ました。DSM の権限では、`homes` の中の1人分だけを許すことはできません。そのため、検索させたいファイルは別の共有フォルダに移しました（[verification.md](verification.md#検索範囲の確認2026-11-04)）。

索引の対象外のフォルダでは、検索結果が0件でも「ファイルがない」とは言えません。対象外の場所は、`find` などでの走査と使い分けます。

## 5. できるようになったことと、前提

エージェントは、NAS の全部のファイルを読まずに、「どのファイルに何が書いてあるか」の候補を JSON で受け取れます。確かめるときは、そのファイルだけを開けば済みます。人が DSM で検索するときと同じ索引を使うので、索引の手入れは Synology 側に任せられ、索引を2つ持たずに済みます。

前提:

1. **索引を作るフォルダを指定しておくこと。** Universal Search は通常、最初から入っていますが、フォルダを指定しないと索引は空で、API を呼べても何も返りません。いちばん大事な設定です
2. **内部の API は公開されていない仕様で、DSM の更新で変わるかもしれません。** そのため、API を呼ぶ部分は CLI の中の1か所にまとめ、壊れたときに直す場所を1つにしました

まだ確かめていないこと（24時間を超えるセッションで DSM 側のログインがもつか、など）は [verification.md](verification.md#まだ確かめていないこと) にまとめています。始めた SSH を切ったあとも検索セッションが動き続けることは、v0.4.0 で確かめました。
